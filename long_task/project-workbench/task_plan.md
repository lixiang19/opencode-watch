## 关键问题
1. 在不引入本地接口服务的前提下，如何让项目级待办与文件树共用同一套目录授权状态？
2. 移动端和 PC 端应如何展示项目级能力，既不打断现有“新建对话”主流程，又能自然容纳待办和文件预览？
3. 第一版要限制到什么程度，才能保证交互完整但不过度设计？

## 已做决策
| Decision | Rationale |
|----------|-----------|
| 采用“项目工作台”作为项目级容器，而不是在项目卡片上持续加按钮和区块 | 项目卡片只适合承载摘要和快速动作，待办与文件树都属于更深一层的项目级能力 |
| 使用浏览器 `File System Access API` 并接受 Chromium + 首次手动授权目录的约束 | 用户已明确接受该限制，且这是不引入接口服务时最可行的本地文件系统方案 |
| 待办数据固定存储为项目根目录下的 `.opchat-todos.json` | 文件名清晰、可扩展、避免污染普通业务文件名 |
| 第一版文件能力仅做只读文件树与简单预览，不做编辑和保存 | 用户已明确不需要编辑；压低复杂度，减少权限和错误处理负担 |
| 移动端用全屏项目页，PC 端用可与聊天面板并存的工作台面板 | 两端的信息密度与操作路径差异较大，不适合强行共用同一布局 |

## 注意事项
- 后续开发必须保持“无本地接口服务”的约束
- 第一版不做文本编辑、文件保存、全文搜索、拖拽等扩展能力
- 目录句柄按项目目录独立管理，不能用全局单例权限兜底
- 只在 Chromium 体验上作为主路径设计，其他浏览器仅做降级提示
