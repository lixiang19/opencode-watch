# 远程网页连接本机 Opencode 与图片上传 方案

- 状态：草案
- 日期：2026-03-12
- Owner：用户 / OpenCode
- 目标版本/里程碑：远程移动端接入第一期

## 1. 背景与问题

- 背景：希望把网页部署在服务器上，由手机访问，但实际使用的 opencode 服务仍运行在当前电脑上。
- 现象/痛点：现有项目默认是“本机浏览器直连本机 `opencode serve`”，不适合“手机 + 服务器 + 电脑”三设备链路；同时后续希望支持手机上传图片给 AI。
- 成功定义：在不破坏现有本机直连能力的前提下，明确三设备网络架构、图片上传路径和后续开发边界。

## 2. 目标与非目标

- 目标：
  - 明确三设备场景下可落地的网络拓扑与推荐方案。
  - 明确“手机上传图片给 AI”是否需要后端，以及后端最小职责。
  - 为后续开发拆出可执行里程碑，避免一开始就写错架构。
- 非目标：
  - 本文不直接实现上传、代理、隧道或鉴权代码。
  - 本文不替代正式的接口联调结论；涉及 opencode 图片 part 能力仍需二次验证。

## 4. 资料与依据（Librarian）

- 关键结论：
  - `opencode serve` 默认监听 `127.0.0.1`，可通过 `--hostname`、`--cors`、Basic Auth 调整对外访问能力；见官方 Server 文档：`https://opencode.ai/docs/server/`。
  - `opencode web` 官方也默认仅本机访问；若开放局域网/网络访问，需要显式配置 `0.0.0.0` 和认证；见官方 Web 文档：`https://opencode.ai/docs/web/`。
  - 浏览器里部署在服务器上的网页，其 API 调用实际由访问该页面的设备发起；因此“三设备场景”下若前端直连 opencode，本质是“手机 -> 电脑”，不是“服务器 -> 电脑”。
  - 若要让手机稳定访问电脑上的 opencode，通常需要公网隧道、VPN 或服务器代理；其中服务器代理更适合统一鉴权、日志和上传。
  - 若只是让 AI 看图，理论上前端可直接上传图片内容；但若要让电脑侧 opencode 后续继续操作该图片文件，仍需要一层把文件真正落盘到电脑的桥接服务。

## 5. 方案概览（主方案）

### 5.1 方案摘要

- 一句话：采用“手机只连服务器，服务器做代理/中转，电脑运行 opencode 与图片落盘桥接”的标准三层方案。
- 取舍：相比手机直接连电脑隧道，这个方案开发量略高，但网络路径更稳定、鉴权更集中、图片上传也更自然。
- 影响面：会新增服务端代理/上传接口，前端需要支持图片选择与附件状态，电脑侧需要一个最小接收端或由现有服务扩展接收能力。

### 5.2 风险与回滚

- 风险：
  - opencode 当前公开文档未明确暴露图片消息 part 的完整调用方式：先用桥接上传 + 文件路径方案缓解。
  - SSE 经过反向代理时可能被缓冲或超时：代理层显式关闭 buffering、拉长超时缓解。
  - 电脑暴露能力到外网后存在安全风险：通过服务器集中鉴权，电脑侧仅接受来自受控隧道/VPN/反向连接的请求缓解。
  - 图片上传链路可能出现大文件、断网、重复上传问题：通过大小限制、临时文件目录、上传态和重试策略缓解。
- 回滚：
  - 保留现有“本机浏览器直连本机 opencode”模式，不替换现有 dev/本地使用路径。
  - 新的移动端远程能力通过独立配置开关启用，出现问题时可退回纯文本直连模式。

## 6. 详细设计（Spec）

### 6.1 交互/行为（如适用）

- 用户流程：
  - 手机打开服务器上的网页。
  - 用户登录后进入会话页，网页只与服务器域名通信。
  - 用户发送文本时，服务器将请求转发到电脑上的 opencode 服务，并把 SSE 流回传给手机。
  - 用户上传图片时，网页先把图片传到服务器上传接口；服务器再把图片安全中转到电脑侧桥接服务落盘。
  - 桥接服务返回本地文件路径或附件标识；随后服务器调用 opencode 发消息，把该图片作为上下文的一部分交给 AI。
- 边界条件：
  - 手机网络抖动时，上传与 SSE 需分别提示失败，不可混成“AI 挂了”。
  - 非图片文件默认拒绝；图片大小、数量、分辨率应有限制。
  - 如果电脑离线，服务器应直接返回“电脑未连接/隧道不可用”，而不是无限等待。

### 6.2 接口与契约

- API/函数签名：
  - `POST /api/opencode/session/:id/prompt`：前端消息请求 -> 服务器 -> 电脑侧 opencode，返回普通 JSON 或建立 SSE。
  - `GET /api/opencode/event`：前端订阅事件流 -> 服务器代理 opencode SSE。
  - `POST /api/upload/image`：前端上传手机图片 -> 服务器。
  - `POST /api/bridge/upload`：服务器转发图片到电脑侧桥接服务，返回 `{ filePath }` 或 `{ attachmentId }`。
  - `POST /api/opencode/session/:id/prompt-with-image`：服务器组装文本 + 图片上下文后调用 opencode。
- 错误码/异常：
  - `400`：文件类型、大小或参数不合法。
  - `401/403`：登录态失效或桥接认证失败。
  - `409`：电脑侧当前忙或会话状态冲突。
  - `502/504`：服务器到电脑链路断开、SSE 超时、桥接不可达。

### 6.3 数据与存储（如适用）

- Schema/字段：
  - `uploadToken`：字符串（短期有效，绑定用户和会话）。
  - `filePath`：字符串（电脑侧真实落盘路径，仅服务端可见）。
  - `attachmentId`：字符串（可选，用于隐藏真实路径）。
  - `mimeType`：字符串（必须为 `image/*`）。
  - `size`：数字（受限，例如 10MB 内）。
- 迁移策略：
  - 第一阶段可不建数据库，先走临时文件 + 内存映射。
  - 第二阶段若需要历史附件、去重或过期回收，再补持久化表。

### 6.4 兼容性与发布

- 兼容策略：保留现有 `serverUrl` 直连模式，同时新增“server relay mode”；通过环境变量或设置页切换。
- 发布步骤：
  - 先发布服务器代理文本链路。
  - 再发布图片上传到电脑侧桥接。
  - 最后再接入 opencode 图片消息或文件上下文方案。

### 6.5 可观测性

- 日志：记录 `requestId`、会话 ID、上传文件大小、代理耗时、SSE 断流原因。
- 指标：上传成功率、上传耗时、SSE 建连成功率、电脑在线率、桥接失败率。
- 告警：电脑离线超过阈值、上传错误率异常升高、代理 5xx 持续出现。

## 7. 验收标准（必须可验证）

- 功能验收：
  - [ ] 手机访问服务器网页后，纯文本消息可经服务器成功转发到电脑侧 opencode，并返回完整结果。
  - [ ] 手机上传一张图片后，图片可成功到达电脑侧并生成可追踪的本地路径或附件标识。
  - [ ] 用户能在同一会话中发送“文本 + 图片”请求，AI 能基于图片上下文回复。
  - [ ] 当电脑离线、上传失败、认证失败时，前端能给出明确错误提示。
- 非功能验收：
  - [ ] 性能：单张常规手机图片上传首包响应可在可接受范围内完成，SSE 首次建连无明显卡顿。
  - [ ] 可靠性：电脑短暂断网后，前端能识别失败并允许重新连接或重试上传。
  - [ ] 安全：电脑侧服务不直接裸暴露公网，上传与代理链路都有认证和来源控制。

## 8. 里程碑与任务（Milestones）

> 原则：只拆 1-3 个里程碑；每个里程碑都必须有可验证的交付物与退出标准。里程碑内再列任务，但不要过度细碎。

### M1：打通三设备文本链路

- 交付物：手机 -> 服务器 -> 电脑 opencode 的纯文本可用链路。
- 退出标准：手机能稳定收发文本消息，SSE 经服务器代理后可正常显示。
- 任务：
  - [ ] 设计并实现服务器代理 opencode 的基础接口（文件/模块：待定服务端）验收：手机能建立会话并发送纯文本。
  - [ ] 配置电脑侧到服务器的可达链路（文件/模块：待定部署配置）验收：服务器可访问电脑 opencode，但公网不可直接裸访。
  - [ ] 增加前端 relay mode 配置（文件/模块：`src/composables/useOpencodeApp.ts`、设置页）验收：可切换直连和代理两种模式。

### M2：打通手机图片到电脑落盘

- 交付物：上传接口 + 电脑侧桥接服务 + 临时文件落盘。
- 退出标准：手机选择图片后，电脑侧能收到并保存文件，服务端拿到可用于后续 AI 调用的返回值。
- 任务：
  - [ ] 设计上传协议与鉴权（文件/模块：待定服务端）验收：未授权请求无法上传。
  - [ ] 实现电脑侧最小桥接接收器（文件/模块：待定电脑侧服务）验收：图片可保存到临时目录并返回路径/ID。
  - [ ] 前端补齐图片选择与上传状态（文件/模块：聊天输入区）验收：手机上可选图、看到上传中和失败态。

### M3：接入图片上下文到 AI 会话

- 交付物：文本 + 图片联合提问能力。
- 退出标准：完成一次真实“手机拍照/选图 -> 上传 -> AI 回答”的闭环。
- 任务：
  - [ ] 验证 opencode 是否支持直接图片 part；若不支持，则实现文件路径/附件注入方案（文件/模块：待定服务端 + 前端）验收：至少一种方案稳定可用。
  - [ ] 为图片消息补齐错误提示和重试策略（文件/模块：聊天消息流）验收：失败后不会出现会话卡死或静默失败。

## 9. 执行计划与闭环

- 执行顺序：M1 -> M2 -> M3
- 每个里程碑验证：
  - M1：用手机访问测试域名，验证文本发送、SSE 返回、断线提示。
  - M2：用手机上传真实照片，验证服务器日志、电脑侧落盘和返回值。
  - M3：在同一会话发送图片相关问题，验证 AI 确实基于图片作答。
- 最终回报：变更摘要 + 验收勾选 + 风险残留 + 下一步
